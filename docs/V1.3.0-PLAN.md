## 1. Inspection false positives

### 1.1 Macro calls must not be arity-checked (A) — 4 reports

`Athena`'s route macros take arbitrary named arguments:

```crystal
get("/with-ann", return_type: Nil) { }
```

`get` is a macro, so there is no parameter list — but the argument-count inspection
reports `Unknown named argument 'return_type'`. Same for `array_of rules, path : ...`.

`CrystalMacroSetters.kt` already has this precedent for configuration blocks
("the entry name resolves only by accident"). Widen the rule: **if the callee resolves
to a `CrystalMacroDefinition`, skip arity checking entirely** — the macro body generates
the real method.

Branch: `feature/1.3.0-macro-calls`. Test: a macro accepting arbitrary named args reports
nothing; a real method with a wrong named arg still reports.

### 1.2 Inherited `initialize` (B) — 11 reports

A call on a subclass is checked against the abstract parent's `initialize`, losing the
subclass's own parameters. Typical: `Athena::ORM::Query::Hints` defines
`def initialize(...)` and subclasses add nothing — but `Part::Abstract` uses
`macro inherited` to inject `def ==`.

Fix: when the constructor overloads come from a parent, walk the hierarchy for an
`initialize` declared on the receiver class itself first, and only fall back to the
parent when the subclass declares none.

Branch: `feature/1.3.0-inherited-init`.

### 1.3 Reads inside range/slice expressions (G) — ~10 reports

The single worst false positive, because the shape is everywhere:

```crystal
cond_end_pos = source.pos(cond_end_location, end: true)
else_begin_pos = source.pos(else_location)
body_range = cond_end_pos...else_begin_pos      # reported: 'cond_end_pos' is never used
```

`CrystalUnusedVarReads` does not treat the operands of a `RANGE_EXPRESSION` (or an index
expression `line[dedent..]`) as reads. Fix the read walker, not the report site.

Branch: `feature/1.3.0-unused-reads`. Also covers H (assignment inside a macro body /
later block pass) — same walker, narrower shapes, ~6 reports.

### 1.4 Summary for the release notes

76 of 100 reports disappear from a real project when §1.1–1.3 and §2.1–2.2 land.

## 2. Expression type resolution

### 2.1 A call's type must not fall back to its receiver (C/D/E/F) — 11 reports

Four separate-looking reports share one bug in `CrystalExpressionTypeResolver`:

| Symptom | Report |
| --- | --- |
| `ids.size + 3` → "got `Enumerable(String)`" | `stream.cr:486` |
| `@read_xml.call("")` → "got `Proc(String, String)`" | `reset.cr:213` |
| `db.query_one?(..., as: ...)` → "got `DB::Database`" | `user_repository.cr:46` |
| `row[0]` on a tuple → "got `{Int64, String, Int32}`" | `emulator_pool.cr:160` |

Each one is the *receiver's* type being reported as the *call's* result.

Confirmed against stdlib: `Enumerable#size : Int32` exists
(`enumerable.cr:1698`), so `size` should resolve — but `lookupReturnTypeInClass` looks up
`CrystalMethodByClassIndex` by the short class name and returns `null` when no method
carries an explicit return annotation, and **`null` then silently becomes the receiver's
type further up**. That last step is the bug: unknown must stay unknown.

Fix, in order:
1. Make `resolveScopedOrFallback` return `null` (unknown) rather than the receiver type
   when the class-scoped lookup misses. **This alone should silence C, E and most of F.**
2. Seed `FIXED_RETURN_TYPES` with the receiver-independent stdlib methods that have no
   annotation in the index but a fixed yield: `size`/`count`/`length` → `Int32`,
   `empty?`/`any?`/`none?` → `Bool`, `keys`/`values`, `first`/`last`/`min`/`max` (these
   return the element type — handle via the receiver's generic argument, or leave unknown
   rather than guess).
3. `as:` on `query_one?`/`query_all` — the named argument *is* the return type. Read it.

Branch: `feature/1.3.0-expression-types`. Tests: one per row of the table above, plus a
negative test that an unknown call type stays unknown (does not become the receiver).

### 2.2 Tuple indexing (D) — 3 reports

`row[0]` on `{Int64, String, Int32}` must yield `Int64`. Needs the tuple type's element
list carried through resolution instead of only its text. Do this **after** §2.1.

Branch: `feature/1.3.0-tuple-index`.

## 4. Performance

### 4.1 Shards are libraries, not sources (biggest win)

`CrystalStdlibLibraryProvider` registers **only the stdlib** as an
`AdditionalLibraryRootsProvider`. Every `lib/<shard>` is an ordinary content root, so all
1 894 dependency files in this project are inspected. 74 % of the reported problems come
from code the user will never edit, and analysis time is dominated by it.

Fix: register each `lib/<shard>` (or the whole `lib/`) as a project library, the way the
stdlib already is — indexed and navigable, but not inspected.

Must not break: `lib/<shard>/src` is editable source the user may deliberately inspect,
and `CrystalRequireResolver` special-cases that path for `require` resolution.

Branch: `feature/1.3.0-shard-libraries`. **Measure first** (see §5) — this is the largest
change and the least understood.

### 4.2 Narrow the search scope

26 call sites use `GlobalSearchScope.allScope(project)` for every stub-index lookup.
`ProjectAndLibrariesScope` is not used anywhere in the codebase.

Fix: replace with `ProjectAndLibrariesScope(project)` (one line per site, 26 sites), and
add a helper so the next lookup does not reinvent it. Correct only after §4.1 (libraries
in, excluded dirs out).

Branch: `feature/1.3.0-scope-narrowing`.

### 4.3 Cache the three hot lookups

Confirmed: `CrystalTypeHierarchy`, `CrystalMethodLookup` and `CrystalOverloadEvaluator`
have **no** caching, and only 5 files in `main/kotlin` use `CachedValuesManager` at all.
The inspected path hits a stub index **once per `.`-call in the file**:

```
CrystalTypeCheckInspection
  → CrystalDotCallOverloads.resolve
  → CrystalOverloadEvaluator.findCandidateMethods
  → StubIndex.getElements(..., allScope(project))
```

and the argument-count inspection repeats the same lookups because nothing is shared.

Fix: `CachedValuesManager`-backed cache keyed by `(methodName, receiverType)` on the
project, shared by both inspections.

Branch: `feature/1.3.0-lookup-cache`.
